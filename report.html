Recap of Assignment 1. A consumer finance company needs a real-time service that estimates each credit card applicant's probability of defaulting next month. The service maps that probability to APPROVE (< 0.30), REVIEW (0.30–0.60) or DECLINE (≥ 0.60). The lab implementation has an Airflow training pipeline tracked in MLflow; the proposed serving architecture would load the @champion alias through a FastAPI service monitored with Prometheus and Grafana. The primary metric is ROC AUC (target ≥ 0.75), with PR AUC, recall at the 0.30 threshold, Brier score and a fairness gate (selection-rate gap between sexes ≤ 0.10).
Refinements in this document: (1) Lab 2 CLI training, evaluation and the Airflow DAG use the shared prepare_features function before the sklearn Pipeline; this assignment's experiment script calls the same underlying add_derived_features function. Lab 4 moves feature derivation inside its Pipeline. (2) Validation is an explicit three-level gate before training. (3) The registry uses aliases instead of deprecated stages. (4) The Lab 2 CLI registers rejected candidates by default for an audit trail, while the DAG skips registration after a failed quality gate. 1.3 Design rationale

  • Validation before training, not just after ingestion. The expensive and risky step is training and promotion. A degenerate target (all zeros) still trains "successfully" and scores 100% accuracy. Placing the gate directly upstream of training guarantees that no model is produced from data that failed a check, and its report travels with the run as an artifact.
  • Modularity and reuse. Core validation, feature derivation and evaluation functions live in the pipeline/ package. The CLI runner and Airflow DAG reuse them; this assignment's sweep uses the same underlying feature derivation. Tracking and orchestration still have side effects and separate wrappers.
  • Error handling and recovery. Validators return lists of errors, so one run reports every problem at once. Airflow retries transient failures once after 2 minutes. A failed task stops everything downstream. The cleanup task uses none_failed_min_one_success, so it runs on either branch. The champion alias is changed only after the quality gate passes; an MLflow logging failure can still leave a partial run to inspect.
  • Scalability. Stages exchange files on a shared volume and pass only metadata through XCom, so they can move to separate workers (LocalExecutor now, CeleryExecutor or KubernetesExecutor later). The prototype has 30,000 rows, and the tested HistGradientBoosting runs trained on 24,000 rows in under a second here. A larger dataset would require new memory and runtime measurements before choosing Spark or another architecture.

2.1 Experiment design

Variables: algorithm family (Dummy, LogisticRegression, RandomForest, HistGradientBoosting); hyperparameters (C, depth, trees, learning rate, L2); features (23 raw vs 29 with the engineered features); preprocessing and imbalance handling (class_weight="balanced"). 2.2 Metrics strategy

  • Primary: ROC AUC. It is independent of the threshold and measures ranking quality. The business applies its own thresholds, so ranking is what the model owes it.
  • Secondary: PR AUC (sensitive to the 23% minority class, which is where the losses are); precision and recall at 0.30 (the REVIEW threshold: recall is the share of future defaulters stopped, precision the share of flagged applicants who really default); Brier score (the thresholds act on raw probabilities, so calibration matters); training time and per-row latency (operating cost).
  • Guardrail: fairness gap. The maximum difference in selection rate (score ≥ 0.30) between SEX groups. It is a hard gate at 0.10.
  • Link to the business. Recall at 0.30 maps to the loss reduction goal, the flag rate (TP + FP)/N maps to the manual review workload goal, and the fairness gap maps to the compliance goal. A 0.01 gain in AUC matters only if it does not push the review rate or the fairness gap past their limits.

def promote_model(run_id: str, metrics: Dict[str, float],
                  model_name: str = "credit-default-classifier") -> Dict[str, Any]:
    client = MlflowClient()
    gate = passes_quality_gate(metrics)                  # missing metric => fail (fail closed)
    version = mlflow.register_model(f"runs:/{run_id}/model", model_name).version
    if not gate["passed"]:
        outcome = "rejected"                             # registered for the audit trail, no alias
    elif beats_champion(metrics, model_name, margin=0.002):
        outcome = "champion"
        client.set_registered_model_alias(model_name, "champion", version)
    else:
        outcome = "challenger"
        client.set_registered_model_alias(model_name, "challenger", version)
    client.set_model_version_tag(model_name, version, "quality_gate",
                                 "passed" if gate["passed"] else "failed")
    client.set_model_version_tag(model_name, version, "outcome", outcome)
    return {"version": version, "outcome": outcome, "quality_gate": gate}

# serving loads by alias, never by a hard-coded version number
model = mlflow.sklearn.load_model("models:/credit-default-classifier@champion")

Versioning convention. There is one registered model per use case (credit-default-classifier), with versions numbered automatically. The alias @champion is what serving loads and @challenger is the next candidate. The tags quality_gate, outcome and failed_checks record why each version was or was not promoted. Every version links back to its run, and so to its parameters, data statistics, validation report and feature list.

2.5 Analysis

  • Every trained model beats the baseline by a wide margin (AUC about +0.25, PR AUC more than doubles), but the families differ by at most 0.006 AUC on this test split. No uncertainty interval or paired significance test was calculated, so this run alone does not establish that one family ranks risks better. Other metrics matter.
  • Derived features help logistic regression on this split. The ratios lift its ROC AUC from 0.745 to 0.751 (E1 → E2). The tested HGB configuration did not improve with them (E7 → E8); tree splits may already capture part of their effect. Changing C from 1.0 to 0.1 made no meaningful difference in these test metrics.
  • class_weight="balanced" changes the operating point, not the ranking. E4 has the same AUC as E2, but its probabilities are no longer calibrated (Brier 0.19 against 0.14). At the 0.30 threshold it flags most applicants: recall 0.90, precision 0.29. That would roughly triple the manual review queue and widen the fairness gap to 0.081. Recall should be adjusted by moving the threshold, not by breaking calibration.
  • Accuracy vs fairness. The most accurate family (logistic regression, gap 0.054–0.056) treats the two groups least evenly. The tree ensembles cut the gap roughly in half (0.028–0.035) for at most 0.004 AUC. All models pass the 0.10 gate, so the gate alone does not decide; the business priority does.
  • Cost. Every candidate scores in under 11 µs per row, far inside the 100 ms budget. Random forests are the slowest to train and score, and their model files are the largest.

Recommendation for a future registry decision: E9 (HistGradientBoosting on engineered features, lr 0.03, depth 8, L2 2.0) as @champion, with E2 (logistic regression) as @challenger. E9 has the narrowest fairness gap (0.028, about half of E2's). Its AUC is 0.0036 below E2 on this split; no uncertainty test was run. Its Brier score (0.145) is close to E2's (0.144), while its precision and recall reflect a different trade-off. Explainability would need to be implemented and verified separately. E2 is a useful challenger candidate because it is simpler; the experiment script tracks runs but does not assign registry aliases.

3. Workflow Orchestration Design

3.1 DAG architecture

TaskDescriptionXCom out (metadata only)
ingestLoad the raw data, split it, write split.joblib and raw.parquet to the per-run directory on the shared volume.run_dir, data_stats
validateThree-level validation with raise_on_error=True; write validation_report.json.validation_report
trainFit the Pipeline inside an MLflow run named airflow-{ds}; dump model.joblib.mlflow_run_id
evaluateMetrics and per-group metrics, logged to the same run; full JSON to disk.metrics (scalars only)
decideApply passes_quality_gate; return the task_id of the next task.quality_gate
promote_modelRegister the model, compare with the champion, set the alias.promotion
skip_promotionEmptyOperator that marks the rejected path.—
cleanupDelete the run directory on either branch.—

Dependencies. The chain is strictly linear up to decide, because each task consumes the previous task's artifact. For example, train must not start unless validate succeeded, which is how a data problem stops a deployment. Only one branch after decide runs. cleanup depends on both branches with none_failed_min_one_success, because the default all_success rule would skip it on every run, since one branch is always skipped.

3.2 Scheduling strategy

  • Trigger types: time-based (@weekly, set by the AIRFLOW_SCHEDULE variable), manual (after a data fix or feature change), and a planned event trigger in which Alertmanager would call the Airflow REST API after significant drift. The event trigger is not implemented in the lab.
  • Frequency: weekly. Labels arrive with a 30–60 day delay, so daily runs would refit almost the same data. Monthly is too slow to respond to campaign-driven drift. catchup=False and max_active_runs=1 prevent overlapping runs from competing for the champion alias.

3.3 Code: DAG, tasks and dependencies

default_args = {"owner": "mlops-team", "depends_on_past": False,
                "retries": 1, "retry_delay": timedelta(minutes=2)}

def validate(**context):
    """Quality gate on the data. Raising here stops the DAG before training."""
    ti = context["ti"]
    run_dir = Path(ti.xcom_pull(task_ids="ingest", key="run_dir"))
    report = validate_dataset(pd.read_parquet(run_dir / "raw.parquet"), raise_on_error=True)
    (run_dir / "validation_report.json").write_text(json.dumps(report, indent=2))
    ti.xcom_push(key="validation_report", value=report)

def evaluate(**context):
    ti = context["ti"]
    run_dir = Path(ti.xcom_pull(task_ids="ingest", key="run_dir"))
    split, model = joblib.load(run_dir / "split.joblib"), joblib.load(run_dir / "model.joblib")
    result = evaluate_model(model, split["X_test"], split["y_test"],
                            run_id=ti.xcom_pull(task_ids="train", key="mlflow_run_id"))
    ti.xcom_push(key="metrics", value={k: v for k, v in result.items() if isinstance(v, (int, float))})
    (run_dir / "evaluation.json").write_text(json.dumps(result, default=str))   # data -> volume

def decide(**context):
    """BranchPythonOperator: must return the task_id to run next."""
    ti = context["ti"]
    gate = passes_quality_gate(ti.xcom_pull(task_ids="evaluate", key="metrics") or {})
    ti.xcom_push(key="quality_gate", value=gate)
    return "promote_model" if gate["passed"] else "skip_promotion"

3.4 Operational considerations

  • Failure handling: one retry with a 2-minute delay for transient errors, such as the MLflow server restarting. Validation errors are not transient, and they fail on retry too, which is intended. Tasks are idempotent because each run writes into its own run_id directory, and the alias change is a single atomic registry call.
  • Alerting (designed, not yet in the lab DAG): an on_failure_callback should post the task, run and log URL to the team channel. The skip_promotion path should post the failed_checks list from the quality_gate XCom, so a rejected model is visible rather than silent. SLA misses (a run longer than 30 minutes) should also be reported.
  • Monitoring: implemented today, the Airflow UI shows run and task duration history and MLflow compares runs over time. Planned: a StatsD exporter that sends DAG success rate and duration to Prometheus, with an alert if no successful run happens within 8 days, which would catch a paused or broken scheduler.
